# Architecture Decision Records

This directory contains Architecture Decision Records (ADRs) for this project. ADRs capture significant technical decisions, their context, and their consequences so future contributors can understand why things are the way they are.

## When to write an ADR

Write an ADR when a decision:

- Affects the architecture, public API, or cross-cutting contracts (schemas, transports, persistence formats).
- Will be difficult or expensive to reverse.
- Could surprise a contributor reading the code without context.
- Resolves a genuine tradeoff between competing approaches.

Do not write an ADR for routine implementation choices, style preferences, or decisions with a single obvious answer.

## Numbering

ADRs are numbered sequentially: `ADR-0001`, `ADR-0002`, etc. The filename follows the pattern `NNNN-short-title.md`. Numbers are never reused, even if an ADR is superseded.

## Referring to code: name the identifier, not the path

An ADR is history. Nothing updates one when the code moves, and
`comment-file-pointers.test.ts` — which holds a backticked filename in a
comment or in `.claude/**` against `git ls-files` — deliberately stops short
of `docs/`, on the ground that documentation is read when somebody goes
looking rather than handed over unasked. So a path written here is
unguarded, and the drift is silent.

**It is also already the norm.** Measured 2026-09-22 across every ADR: 290
backticked file-looking tokens, and **16 ADRs name at least one path that
resolves to nothing.** Some are innocent — a gitignored file, a library
name, a runtime artefact, this file's own `NNNN-short-title.md` placeholder
— but the rest are real: ADR-0002 still points at `shared/api-client.ts` and
`shared/daemon-backend.ts`, which moved into the `daemon-client` package;
ADR-0009 names `canvas-store.ts` and a `meta.ts` its own notes record as
deleted; ADR-0014 names four `references/` modules that have since moved.

So prefer, in descending order of durability:

1. **An identifier** — `chunkSnapshot`, `workspaceDocCache`,
   `COMPACT_DELTA_BYTES`. Survives a file move, and a reader can grep for it.
2. **A quotation** of the code or comment being discussed. The text is its
   own address.
3. **The thing, in prose** — "the daemon's document store", "the web app's
   destructive-copy module". Survives a rename of the file AND of the symbol.
4. **A package name** — `ports`, `apps/web`. Coarse enough to be stable.
5. **A path**, only when the file's LOCATION is itself the decision (a
   migration's own log key, a config file the deployment reads).

This is forward-looking. The sixteen are NOT swept: a decision record is
history, and rewriting the reasoning would misreport what was decided — the
same rule that keeps `slug` and `OpenCanvas` in ADR-0007, 0008 and 0009
behind a dated note. Fix a stale pointer only when you are already editing
that ADR for another reason, and say so.

## Status lifecycle

| Status | Meaning |
|---|---|
| **Proposed** | Under discussion; not yet adopted. |
| **Accepted** | Adopted; the decision is in effect. |
| **Superseded** | Replaced by a later ADR (link to the successor). |

| [ADR-0044](0044-workspace-capacity.md) | A workspace's capacity is an infrastructure limit, refused at the edge and promoted before it | Proposed — the shape is decided and one number deliberately is not. Measured 2026-09-22: NOTHING in this repository refuses a write because a record grew too large, and the only written capacity policy anywhere is a comment for a feature that no longer exists, stating the opposite ("Do not block saves when exceeded"). Three things look like limits and are not — `maxChunkBytes` splits, `COMPACT_DELTA_BYTES` folds, and the 16/24/4 MiB HTTP body limits bound ONE request, so a workspace grows past all of them through many small updates. The forcing case is a keeper on a runtime with a hard ceiling (a Durable Object is 128 MB per isolate, WASM included), which cannot be honoured by warning: past it the write fails and the process may not survive to say why. So capacity is declared by the BACKEND and is not a setting (an operator cannot raise a disk); at the limit the write is REFUSED, reversing the removed soft cap's "warn, never block" for infrastructure limits while keeping it for product-chosen ones; below it a PROMOTION BAND offers migration so the ceiling arrives with warning rather than at it; and a backend may not declare a reachable limit until a migration target and path exist. The band's fraction is left as a measurement rather than a value, per `measured-change` — it follows from how long a migration of that size takes and how fast the record grows, neither measured. Does NOT decide whether a Worker keeper is adopted (ADR-0020's one-container story stands), whether 128 MB suffices, or per-document limits. Rejects automatic splitting (it changes what a workspace IS to solve a storage problem) and automatic migration at the band (ADR-0035 d4 makes changing keeper a governance change, not something a threshold performs for you) |
