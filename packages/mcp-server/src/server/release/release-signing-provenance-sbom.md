# Release Signing, Provenance, and SBOM Policy

## Status

Consolidation complete. No public release has been cut from this path yet.

- `release.yml`: single production path — release-please + npm OIDC provenance
  (`publish-mcp` job) + Docker build/push/SBOM/cosign keyless sign
  (`docker-publish-sign` job).
- `ci.yml`: non-destructive publish dry-run verification (`dry-run-npm` and
  `dry-run-docker` jobs, no OIDC/push/sign).
- `publish-production.yml` and `publish-dry-run.yml` deleted.

## Checksum policy

- **npm tarball**: SHA-512 checksum computed and published automatically by the
  npm registry on `npm publish`. `pnpm pack` output verified locally by
  `check:release-artifacts` before publication.
- **Docker image**: SHA-256 image digest computed and exposed automatically by
  the Docker registry. Referenced in the manifest as `image@sha256:…`.

No custom checksum tooling is required for either artifact in the current slice.

**Acceptance criteria for the publish-workflow slice** (checksum gate is complete when):
- npm tarball: the SHA-512 digest from `npm info @kamiazya/whiteboard-mcp dist.shasum` is
  recorded in the GitHub Release notes and can be verified with
  `npm pack --dry-run && shasum -a 512 <tarball>`.
- Docker image: the `image@sha256:<digest>` reference is recorded in the GitHub Release notes
  and the deployment docs Compose snippet pins the digest rather than a mutable tag.

## Provenance policy

- **npm tarball**: npm provenance (`--provenance` flag on `npm publish`).
  Produces a SLSA Level 2 provenance statement linked to the GitHub Actions
  workflow run via OIDC. Deferred to publish-workflow slice; OIDC token is
  only available in CI.
- **Docker image**: SLSA provenance attached as an OCI attestation via
  `docker/build-push-action` + `docker/attest-build-provenance-action`.
  Deferred to publish-workflow slice.

## SBOM policy

- **npm tarball**: CycloneDX SBOM generated by `@cyclonedx/cyclonedx-npm` (or
  `syft`) and attached as a GitHub Release asset and/or npm provenance
  attestation. Deferred to publish-workflow slice.
- **Docker image**: SBOM attestation attached via `docker buildx build
  --sbom=true` using the `docker/sbom-action`. Deferred to publish-workflow
  slice.

## Signing policy

- **npm tarball**: strategy `npm-provenance` — npm provenance (SLSA2 via OIDC).
  Implemented in CI via `publish-mcp` job in `release.yml`. No custom crypto,
  no long-lived private keys.
- **Docker image**: strategy `keyless-cosign` — Sigstore/cosign keyless signing
  via GitHub Actions OIDC. Implemented in CI via `docker-publish-sign` job in
  `release.yml`. No hardcoded keys, no self-signed certificates.

Forbidden strategies (must not appear in policy or implementation):
- `custom-crypto` — any hand-rolled signing scheme
- `bespoke-signing` — non-standard signature format
- `hardcoded-key` — long-lived private key stored in repo or secrets
- `self-signed-cert` — self-signed certificate for artifact signing

## Non-leak policy

The same fail-closed pattern as the rest of the CLI applies to any future
publish or signing gate:
- signing keys / OIDC tokens / cosign private material must never appear in
  stdout or stderr
- SBOM files are attached to releases, not printed to stdout
- Any gate failure: stdout empty, stderr generic safe copy, exit 1

## What the dry-run skeleton slice implements

- `publish:dry-run:npm` (root package.json) — runs `pnpm pack`, captures
  SHA-512 checksum, writes SBOM placeholder. No registry publish. No OIDC.
- `publish:dry-run:docker` (root package.json) — builds `Dockerfile.server`
  locally (no push), captures image ID. No cosign. Skips gracefully when
  Docker is unavailable.
- `publish:dry-run` (root package.json) — aggregate for `publish:dry-run:npm`
  followed by `publish:dry-run:docker`.
- `publish:npm-provenance` (root package.json) — placeholder; exits 1.
  Reserved for publish-workflow slice (`npm publish --provenance`).
- `publish:docker-sign` (root package.json) — placeholder; exits 1.
  Reserved for publish-workflow slice (cosign keyless signing).
- `ci.yml` dry-run jobs — `dry-run-npm` and `dry-run-docker`.
  No `id-token: write`, no secrets, no registry push, no cosign signing.
- Static drift tests: `publish-dry-run-policy.test.ts` — verifies
  `futureGateId` → script mapping, `implementedNow: false`, no premature
  matrix entry, aggregate segment order, Docker job setup, and safe
  `Object.hasOwn()` lookup for future gate IDs.

## What the production publish workflow v0 implements

- `release.yml` — the consolidated production path for release-please output and
  guarded manual `force_publish_tag` reruns. Both paths validate
  `mcp-server-v<semver>` before checkout and require protected environments.
- `publish-mcp` job — runs `pnpm check:release-candidate`, then
  `npm publish --access public --provenance` under `production-npm`.
- `docker-publish-sign` job — runs `pnpm check:release-candidate:docker`, then buildx
  `push: true` with `sbom: true` / `provenance: true`, followed by cosign
  keyless signing under `production-docker`.
- Static drift tests: `publish-production-policy.test.ts` — verifies
  job-scoped `id-token: write`, protected environments, release/manual tag
  guards, Docker preflight, root permission minimization, and safe
  `force_publish_tag` handling. Standalone publish workflows are deleted and
  guarded against reintroduction.

## What the npm SBOM hardening slice implements

- `packages/mcp-server/scripts/release/generate-npm-sbom.mjs` generates a CycloneDX JSON SBOM
  from a `pnpm deploy --legacy --prod` output, so dependency versions are resolved from
  `pnpm-lock.yaml` rather than re-resolved from semver ranges.
- `pnpm check:release-candidate` runs `pnpm generate:sbom:npm` before `pnpm test`, so
  generated-SBOM regression tests execute in the release-candidate path.
- `sbom-policy.test.ts` checks that generated SBOM content excludes known dev-only
  packages and includes expected production packages.
- `packages/mcp-server/_artifacts/` is ignored because SBOM files are generated
  release artifacts, not source.

## Relationship to release-candidate matrix

`tests/e2e/distribution/release-gate-matrix.json` covers pre-publication
verification (build, smoke, distribution integrity). Supply-chain gates
(signing, SBOM, provenance) are publish-time gates. The production workflow v0
exists, but the root `publish:npm-provenance` and `publish:docker-sign` scripts
remain fail-closed placeholders; therefore `implementedNow` stays false and
those IDs remain outside the matrix until runnable gate commands exist.

The `supply-chain-policy.json` `releaseGateMatrixRef` field links the two
files so drift tests can assert the cross-reference is valid.
