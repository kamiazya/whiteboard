# Gates: local + cloud — the narrative

The long form of the push-gate and cloud-gate paragraph in
`.claude/rules/dev-flow.md` (which keeps the decisions and the guards' names).
It lives here because it is read when a gate's shape is being changed or
questioned, not by every session.

The integrator's push is guarded on two sides. **Local (pre-push, `lefthook`)**: `pnpm verify:git-hooks` + `pnpm -r typecheck` + `pnpm lint` (which holds Biome's `noConsole`; a separate `lint:noconsole` flagged the same files and is gone), plus one single-file vitest guard, `mutation-lane-coverage`, and the whole `arch-lint-node` project (pre-commit formats staged files and runs secretlint). NO test SUITE runs at push (user decision, 2026-09-05): the dev loop ran the nearest layer, CI runs everything (about 5 min wall on main; a PR that touches tests adds the sharded stress job, which scales with the diff), and a push-time suite was the same work twice on a machine the push itself saturates. The single-file guard is an exception because it catches what CI cannot make loud or soon enough — a stale mutation lane's whole symptom is SILENCE — and because it finishes inside the typecheck beside it. That is the bar for a second; being fast is not it. **`arch-lint-node` cleared that bar too** (2026-09-12), on the same ground one scale wider: every guard there reads OTHER packages' source, so the project you changed is by construction the one that does not run the rule you broke — measured, a fixed sleep in an `mcp-server` test leaves `--project mcp-node` green and fails it, and the 800-line file-size budget scans `apps/web/src`, so the web projects never run it either. A whole project rather than a file, and the no-suite rule's reason does not reach it: these scans run no product code, open no port and assert on no clock. Timings, the mutation checks and why it is not scoped to a file list are `lefthook.yml`'s comment and `tools/arch-lint/src/pre-push-entry.test.ts`. `contributing-gate-lists.test.ts` derives `CONTRIBUTING.md`'s list from `lefthook.yml`. **`pnpm check:local` is the fuller local pass** — every gate CI's `check` job runs, plus `pnpm knip` from `verify` (seconds, and it catches the dead export a refactor leaves behind; the rest of `verify` builds and smokes the published artifacts and belongs in CI). It is DERIVED from `ci.yml`, not remembered: `local-gate-command.test.ts` fails when the job gains a step the script does not run. That guard exists because the remembered list actually drifted — a session's habitual five (`typecheck`, `lint`, `lint:noconsole`, `audit`, `knip`) was missing `intent:validate`, `secretlint` and `test:scripts`, and reported green for work whose CI `check` job had not been approximated at all. A local pass that is trusted and wrong is worse than none. **Cloud (post-push)**: GitHub Actions CI (`verify`) + CodeRabbit + AccessLint + WIP + CodeQL. `ci.yml`'s jobs aggregate into ONE required check, `ci-gate` (`tools/checks`): branch protection names CHECKS and a matrix names them per leg, so a shard-count change used to rename a required check and block every merge on one that could no longer report. It judges the run's per-LEG conclusions read back from the Actions API, not `needs.<job>.result`, so a gate's correctness never rests on the undocumented matrix-aggregation question; `ci-gate.test.ts` runs it over two captured real runs, one green and one that really failed — monitor with the `Monitor` tool and triage with the `ci-triage` workflow/skill into Tasks / whiteboard canvases. **Cloud (mutation, report-only)**: `mutation.yml` runs Stryker over `canvas-render`'s property-covered modules — on a PR, scoped to the curated files that diff changed and posted as a sticky comment; weekly, the whole list into an artifact. It is deliberately NOT a gate — a mutation score belongs to the whole suite, not to whoever pushed last — and it exists because a property that asserts nothing passes every other gate there is. Its survivors are triaged like review findings, and each is verified by hand first (the tool can report a false survivor; see `package-canvas-render.md`). **Cloud (SonarQube Cloud, report-only)**: `sonarqube.yml` + `sonar-project.properties` — duplication, the maintainability ratings and coverage over time, which no other rung here measures. NOT in `ci-gate`'s `needs`, so it gates nothing until someone adds its check to branch protection. Coverage is `pnpm coverage`; the traps are in `docs/contributing/testing.md`. A pull request whose diff touches only what `sonar.exclusions` excludes (and Markdown) skips the analysis's costly steps — `tools/checks/src/sonar-analysis-inputs.mjs`, fail-open, never on the default branch; the job's `timeout-minutes` is held at 1.5x the newest measured run (1652-1682s on main), because a run that hits the limit is cancelled, not failed. **Cloud (advisory watch, scheduled)**: `audit.yml` runs `pnpm audit:prod` — byte-identically to the `check` job's step, which `scheduled-audit.test.ts` holds — daily against the default branch, because the advisory database moves while the tree stands still. Measured 2026-09-19: an advisory published two days after main's last `check` turned EVERY open branch red at once with nothing in any diff to explain it, and the next person to push paid the triage. Dependabot's alert fires, but it says a package is vulnerable, not that the merge gate is about to fail for everyone, and for a transitive package behind a `pnpm-workspace.yaml` override it opens no PR at all — only the override BOUND moves. The scheduled failure's notification is the whole mechanism; there is no issue to file, per the no-GitHub-Issues policy.

## Runner images are pinned

Every Linux `runs-on` in `.github/workflows` is `ubuntu-24.04`, and the one Windows job (`native-host-windows`) is `windows-2025`; `ci-policy.test.ts` fails on a floating label or an unledgered expression. Decided 2026-10-04, ahead of GitHub moving the `ubuntu-latest` label to Ubuntu 26 on 2026-10-19 (the annotation every job carried). Jobs here depend on what the image ships — `/usr/bin/google-chrome-stable` (the browser and extension jobs), `$GECKOWEBDRIVER` with Mozilla's Firefox rather than the snap (the Firefox smoke), apt's `imagemagick`, docker buildx and cosign (the dry-run and release image jobs) — so a floating label turns an image change into a red `ci-gate` with nothing in any diff to explain it. A pin makes the move a reviewed PR. macOS is not used by any workflow.

**Moving to a newer image** (Ubuntu 26, or 24.04's end of life): do not edit the sites first. Open a PR that adds `workflow_dispatch` to `ci.yml` if absent, change the `runs-on` lines on that branch only, and dispatch `ci.yml` on the branch — the Chrome path, the Firefox driver variable, `imagemagick` and the docker steps each fail by name when the image moved them. Fix what the trial shows, then merge the label change as its own PR so the next red gate has one candidate cause. The `release.yml` and preview jobs do not run on a branch trial; read their image-dependent steps (docker buildx, cosign) against the new image's published software list instead.
